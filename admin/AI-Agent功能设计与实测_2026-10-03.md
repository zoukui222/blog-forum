# AI Agent 功能设计与实测记录

日期：2026-10-03
分支：`feat/ai-agent`（基线 `main @ 8e6b782`）
模型：DeepSeek `deepseek-chat`（OpenAI 兼容 Chat Completions 协议）

---

## 一、做了什么

在博客系统里接入一个**工具型（function calling）AI 助手**。用户在右下角悬浮面板里用自然语言提问，
模型自行决定调用哪些站内工具、拿真实数据后再作答，全过程 SSE 流式输出。

前台访客与后台管理员共用同一个入口（挂在 `App.vue`，登录/注册/移动端不挂）。

四个工具覆盖了「查、读、统、写」四类能力，其中写操作有角色门槛。

## 二、请求链路

```
浏览器  ──GET /ai/chat?message=xxx──►  AiAgentController.chat()
                                          │
                                          ├─ ① 主线程内取身份快照（必须在请求线程做）
                                          │     TokenUtils.getCurrentUser() → AgentContext
                                          │
                                          └─ ② 丢给 aiAgentExecutor 线程池
                                                AiAgentService.run()
                                                  │
                                                  ├─ 写一条 ai_chat_log（RUNNING）拿主键
                                                  │
                                                  └─ 循环（最多 5 轮）
                                                       DeepSeekClient.chatStream(messages, tools)
                                                         │
                                        ┌────────────────┴────────────────┐
                                        ▼                                 ▼
                              返回 tool_calls                      无 tool_calls
                                        │                                 │
                              ToolRegistry.invoke()                 正文增量 → SSE content
                                        │                                 │
                            执行工具 + 落审计日志                    回填 ai_chat_log + done
                                        │
                             结果作为 role=tool 塞回 messages ──► 下一轮
```

SSE 事件类型：`meta` / `tool_call` / `tool_result` / `content` / `done` / `error`。

前端不用原生 `EventSource`，改用 `fetch` + `ReadableStream` 手动解析 SSE 报文——
因为 `EventSource` 只能发 GET 且**不能设置请求头**，而本项目的 token 走 header。

## 四、关键设计决策（面试重点）

### 1. SSE 异步线程里 `ThreadLocal` 会失效

`TokenUtils.getCurrentUser()` 底层是 `RequestContextHolder`（ThreadLocal），只在处理 HTTP 请求的
那条线程上有效。Agent 为了流式输出必须换线程执行，工具一旦跑在别的线程上，
`RequestContextHolder` 就是空的 —— `TokenUtils` 会**静默返回一个空 `Account`**（catch 住异常），
结果是不报错、但 `role` 为 null、`userId` 为 null：
权限判断全部失效、创建出来的文章没有作者。

**处理**：在 Controller 的请求线程里一次性把身份物化成 `AgentContext`，作为参数显式传下去，
全程不碰 ThreadLocal（`AiAgentController.chat()` 第 61 行 → `AgentContext`）。
实测证据见第七节「写操作」——文章落库时 `user_id=1`，证明上下文穿透到了线程池里。

### 2. 流式 function calling 的 `arguments` 是分片到达的

SSE 里 `tool_calls` 是按 `index` 分片下发的：第一片带 `id` 和 `function.name`，
后续片只带 `function.arguments` 的**字符串片段**。必须先按 index 聚合、再把参数片段拼起来，
拼完才是合法 JSON。

`DeepSeekClient.parseSse()` 用 `Map<Integer, AiToolCall>` + `Map<Integer, StringBuilder>`
做聚合，这是流式 function calling 最容易踩的坑。

### 3. `token` 在拦截器与业务层之间不一致（改造中发现并修复的真实缺陷）

`JwtInterceptor` 认证时支持从 **URL 参数**取 token（第 50-52 行），
但 `TokenUtils.getCurrentUser()` **只从 header 取**。两者不一致的直接后果：
认证放行了，业务层却拿不到当前用户。

这个缺陷在原有页面上不会暴露（前端统一走 header），但 SSE 场景下 `EventSource` 无法设置请求头，
token 只能放参数，问题立刻显现 —— 表现为「管理员调用写工具被当成无权」。
已在 `TokenUtils` 补上参数兜底分支（与拦截器对齐，纯新增，不影响任何现有行为）。

### 4. `SseEmitter` 直接发 `String` 会中文乱码

`SseEmitter.event().data(String)` 会走 `StringHttpMessageConverter`，
其默认字符集是 **ISO-8859-1**，中文回答会全部变成乱码。
必须用 `.data(对象, MediaType.APPLICATION_JSON)` 交给 Jackson 转换器输出 UTF-8
（`SseAgentListener.send()`）。

### 5. 工具声明的角色裁剪 + 执行层二次校验

两道关：
- 声明层：`ToolRegistry.buildToolSpec(ctx)` 对普通用户**不返回** `create_blog_draft`，
  模型连它存在都不知道，从源头避免注定失败的调用；
- 执行层：`ToolRegistry.invoke()` 再校验一次 `adminOnly() && !ctx.isAdmin()`，
  防止绕过声明直接构造调用。

实测：管理员 `available=4`，普通用户 `available=3`（同一次构建的不同角色视角）。

### 6. 轮次熔断 + 收口兜底

模型可能反复调同一个工具（尤其查询结果为空时）。两道约束：
- `ai.max-iterations: 5` 硬上限；
- 触达上限后再补一次**不带工具**的请求，逼模型用已有信息作答，
  避免给用户一个空白回复。

### 7. 工具结果截断

一次工具调用可能返回几万字，直接回灌会把上下文撑爆。
`ai.tool-result-limit: 4000` 截断后才塞回 messages（审计表里另存一份 2000 字的记录）。

### 8. 独立线程池隔离

SSE 是长连接，一次对话几十秒全程占用线程。若跑在 Tomcat 请求线程上，
少量并发就能把 Web 线程池占满，拖垮登录、列表等普通接口。
`AiExecutorConfig` 单独开池（核心 4 / 最大 16 / 队列 50 / CallerRunsPolicy）。

### 9. 全链路审计

两张表回答「它到底查了什么、看到了什么、花了多少」：
- `ai_chat_log`：提问、回答、工具轮次、token 消耗、端到端耗时、状态
- `ai_tool_call_log`：每次工具调用的入参、返回、成功与否、耗时

## 六、配置

`application.yml` 新增 `ai.*` 段，密钥不入版本库：

```yaml
ai:
  base-url: ${AI_BASE_URL:https://api.deepseek.com}
  api-key: ${AI_API_KEY:}          # 本地写在 application-local.yml（已 gitignore）
  model: ${AI_MODEL:deepseek-chat}
  max-iterations: 5
  tool-result-limit: 4000
  audit-enabled: true
```

另加 `spring.mvc.async.request-timeout: 300000` —— 容器默认 30s 会把 SSE 长连接提前掐断。

## 七、实测记录（2026-10-03，DeepSeek 真实 API）

### 只读链路（管理员）

提问「站内有哪些关于 Vue 的文章？」：
```
meta   → tools=[get_blog_detail, create_blog_draft, search_blogs, get_blog_stats]
tool_call   search_blogs {"keyword":"Vue","limit":10}            ← 模型自主选工具、自主定参数
tool_result success=true  durationMs=18
content 流式输出 …… done  1 次工具调用 · 1875ms · 1794+189 tokens
```
回答引用了真实数据：`id=12《解密ECharts甘特图…》 作者:管理员 分类:前端 阅读:16`。

### 写操作（管理员）—— 同时验证跨线程用户上下文

提问「帮我创建一篇新文章，标题《AI Agent 接入实践》…」：
```
tool_call   create_blog_draft  → tool_result success=true  durationMs=20
```
数据库核对：
```
blog 表新增 id=22，title=AI Agent 落地实践：从概念到生产，user_id=1，category_id=7，
date=2026-10-03，read_count=0，content 长度 2154 字，descr 自动生成
```
**`user_id=1` 是关键证据**：证明 `AgentContext` 穿透线程池成功。
（该测试数据已删除，blog 表恢复为 5 篇。）

### 权限拦截（普通用户）

同一句「帮我创建一篇新文章…」，用 `light`（USER）账号：
```
meta → tools=[get_blog_detail, search_blogs, get_blog_stats]   ← 写工具不可见
done → iterations=0，直接说明无权限（47 tokens，623ms）
```

### 只读工具（普通用户）

提问「这个站一共多少篇文章？总阅读量是多少？」：
```

注册用户数 3 / 分类数 9 + 分类分布 + 阅读量 Top5
```

（统计中的 6 篇含当时未删除的测试数据；现为 5 篇。）

## 九、已知限制与后续可做

1. **无多轮对话记忆**：每次提问是独立会话，追问「这篇的正文呢」会丢失上文。
   要做需要把历史消息带进请求（表结构已能承载）。
2. **无流式工具进度细化**：目前只有「正在检索…」文案，可加真实进度。
3. **无速率限制**：登录用户可无限提问，生产环境需要按用户限流。
4. **分类映射靠实时查库**：`search_blogs` 的分类说明每次请求都查一次库，可加缓存。
5. **模型偶尔不严格遵循指定字段**：实测中模型把用户指定的标题改写了。
   已在 system prompt 中强化，但并非 100% 可靠，属于模型行为层面问题。
