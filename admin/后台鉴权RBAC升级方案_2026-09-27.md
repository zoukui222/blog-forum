# 后台鉴权（RBAC）升级方案

| 项 | 内容 |
| --- | --- |
| 文档日期 | **2026/9/27** |
| 项目 | 基于 Spring Boot + Vue + MyBatis 的博客论坛系统 |
| 用途 | 日常实习（后端 / 全栈）简历项目 · 第一优先级改造项 |
| 当前状态 | **方案定稿，代码零改动**（本轮只做文档与版本控制） |
| 实施时间盒 | 60 分钟（一次性完成，可分两批放量验证） |

---

## 一、为什么第一步选它

它是本项目唯一一个「面试官亲手试两下就能打穿」的问题。三条证据串起来即可完成普通用户到管理员的提权：

1. `common/config/JwtInterceptor.java` 只校验 token 是否有效（用账号密码做 HMAC 验签），**从不校验角色与资源归属**；
2. `service/UserService.java:117` 签发 token 时角色是**硬编码**的：
   `String tokenData = dbUser.getId() + "-" + RoleEnum.USER.name();`
3. `controller/UserController.java` 的 `PUT /user/update` 无归属校验，而 `resources/mapper/UserMapper.xml` 的 `updateById` **允许更新 `role` 字段**（`<if test="role != null">`）。

于是：任何注册用户执行 `PUT /user/update {"id":<自己>,"role":"ADMIN"}` 即自封管理员；前端 `views/Manager.vue:80-95` 仅凭 `localStorage['xm-user'].role === 'ADMIN'` 放行后台菜单，后端全程不拦。**整套权限体系建立在前端一个字符串上。**

## 三、升级目标

把「权限由前端 localStorage 的 role 字段决定」改为「**权限由服务端依据 token 中的真实角色 + 资源归属决定**」，并且不破坏任何一条现存的正常业务路径。

验收标准（三条同时成立）：

- 普通用户：前台全部功能正常，且越权调用管理接口被服务端拒绝；
- 管理员：后台全部功能正常（这是最易翻车的一条，必须手点）；
- 普通用户无法通过任何请求路径改变自己的 `role` 或访问他人资源。

---

## 四、策略：两把不同的锁，绝不用一把锁砸下去

接口按「前台是否调用」分两类，用不同手段处理。分类依据见附录的前台接口调用普查。

| 接口类型 | 处置手段 | 涉及接口 |
| --- | --- | --- |
| 纯管理接口（前台零调用） | **角色拦截：仅 ADMIN** | `/admin/**` 全部；`/user/add`、`/user/delete/**`、`/user/delete/batch`、`/user/selectPage`、`/user/selectAll`；`/category` 的写接口；`/notice` 的写接口；`/activitySign/selectPage`、`/activitySign/delete/{id}`、`/activitySign/delete/batch` |
| 前台与后台共用接口 | **归属校验 + 字段白名单**（不能用角色锁，锁了用户就无法改自己资料） | `/user/update`、`/blog/update`、`/blog/delete/**`、`/comment/deleteDeep/{id}`、`/activitySign/delete/user/{activityId}/{userId}` |
| 只读公开接口 | 保持登录可用即可，不加限制 | `/category/selectAll`、`/notice/selectAll` |

三条必须同时落地的配套改动：

### 4.1 先修 token 角色（前置条件，否则管理员第一个被自己拦在门外）

`service/UserService.java` 的 `login()`：

```java
// 改前：String tokenData = dbUser.getId() + "-" + RoleEnum.USER.name();
// 改后：角色取库中真实值，兜底 USER
String role = ObjectUtil.isNotEmpty(dbUser.getRole()) ? dbUser.getRole() : RoleEnum.USER.name();
String tokenData = dbUser.getId() + "-" + role;
```

`data/user` 表中 `id=1` 的管理员记录 `role='ADMIN'`，修正后管理员登录即可获得真实 ADMIN 角色（老 token 需重新登录一次）。

### 4.2 归属校验 + 字段白名单（一句话堵死自封管理员）

`service/UserService.java` 的 `updateById()` 里增加：

```java
Account currentUser = TokenUtils.getCurrentUser();
if (!RoleEnum.ADMIN.name().equals(currentUser.getRole())) {
    user.setId(currentUser.getId());  // 只能改自己
    user.setRole(null);               // 白名单：不允许改角色
    user.setPassword(null);           // 白名单：改密码走 /updatePassword
}
```

利用 XML 中 `<if test="xxx != null">` 的特性，字段置 `null` 即不参与更新，无需改动 SQL。

其余共用接口同法：

| 接口 | 处理 |
| --- | --- |
| `/activitySign/delete/user/{activityId}/{userId}` | 非 ADMIN 时强制 `userId = 当前用户id`（防取消他人报名） |
| `/blog/delete/{id}`、`/blog/delete/batch`、`/blog/update` | 非 ADMIN 时校验 `blog.userId == 当前用户id`，否则拒绝 |
| `/comment/deleteDeep/{id}` | 非 ADMIN 时校验 `comment.userId == 当前用户id`，否则拒绝 |

### 4.3 渐进放量（保命策略）

**分两批标注注解**，不要一次全上：

- 第一批：`/admin/**`（类级一行即可）与 `/user` 的管理接口 → 跑完验证清单第 1-6 条（前台是否被误伤）；
- 第二批：`/category`、`/notice`、`/activitySign` 的管理接口 → 再跑一遍前台。

任一批验证不过，立即回滚该批（见第七节）。

## 八、保险与回滚

- **回滚前提**：本方案实施前已完成 `git init` 并提交代码基线（2026/9/27 完成），任何一步出问题执行 `git checkout .` 或 `git revert` 即可恢复。
- **老 token 兼容性**：修改 token 角色后，浏览器中已登录的旧 token 仍需重新登录一次，属预期行为，不影响数据与功能。
- **误伤兜底**：若某个前台页面出现 403，说明该接口被错误归入「纯管理接口」，处理方式是把该接口从角色拦截改为归属校验，而不是放开角色限制。

## 九、本轮明确不做（时间盒裁剪，留作后续独立迭代）

| 项 | 原因 |
| --- | --- |
| 密码 BCrypt 加密 | 涉及存量明文数据迁移，需单独时间盒，避免与鉴权改造交叉出问题 |
| 文件上传鉴权与白名单（含 `/files/**` 免登录问题） | 独立风险点，单独一轮处理 |
| `/register` 可注册 ADMIN 的问题 | 属注册接口设计缺陷，与授权改造解耦 |
| 全库 `@Transactional`、Service 层单元测试 | 工时超出本次 60 分钟 |
| `admin` 表与 `user` 表的双轨账号体系合并 | 影响面大，需先明确产品语义 |

## 十、简历描述（本项完成后可写入）

> 将后台权限从「前端 localStorage 的 role 字段」迁移到服务端：基于 Spring Boot 拦截器 + 自定义 `@RequireRole` 注解实现 RBAC，并为用户资料 / 报名 / 内容删除接口补充资源归属校验与字段白名单，修复普通用户可越权调用管理接口、可自改 role 提升为管理员的越权漏洞。

**面试追问的答法**：拦截器通过 `HandlerMethod` 读取注解，token 中的角色回库校验；后台独有接口用角色拦截，前台与后台共用的接口用资源归属校验 —— 因为普通用户同样需要修改自己的资料，用角色锁会导致正常功能不可用。要点是分清「认证」与「授权」。

## 附录：前台接口调用普查（支撑「不会锁死前台」的结论）

对 `vue/src/views/front`、`vue/src/views/mobile`、`vue/src/components` 全量检索后端接口调用，普通用户路径实际用到的接口仅有：

| 接口 | 调用位置 | 性质 |
| --- | --- | --- |
| `/likes/set`、`/collect/set` | 详情页组件 | 互动，带登录态 |
| `/category/selectAll` | `front/Home.vue`、`front/NewBlog.vue`、`mobile/home.vue` | 只读公开 |
| `/notice/selectAll` | `Front.vue`、`front/Home.vue` | 只读公开 |
| `/user/update` | `components/PersonPage.vue`、`front/Person.vue` | 改自己资料 |
| `/activitySign/add`、`/activitySign/delete/user/{a}/{u}` | `front/ActivityDetail.vue`、`mobile/activityDetail.vue` | 报名 / 取消自己的报名 |
| `/blog/delete/`、`/blog/delete/batch` | 个人中心 | 删自己的博客 |
| `/comment/deleteDeep/` | 个人中心 | 删自己的评论 |
| `/updatePassword` | 个人中心 | 改密码 |

**结论：前台路径不调用任何 `/admin/**` 接口，也不调用 `/user`、`/category`、`/notice`、`/activitySign` 的管理类接口。** 因此按第四节分类收权，不会导致前台功能不可用。
