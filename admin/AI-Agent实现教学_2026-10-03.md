## 第 1 章 先把四个词分清

面试官问「你这个 Agent 怎么做的」，八成是想听你有没有分清这四层：

| 词 | 是什么 | 在你项目里的体现 |
|---|---|---|
| LLM | 会说话的函数，输入文本输出文本 | DeepSeek `deepseek-chat` |
| Prompt | 你塞给模型的话 | `AiAgentService.buildSystemPrompt()` |
| Function Calling | 让模型**说出**它想调用哪个函数、参数是什么 | `tools` 数组 + 响应里的 `tool_calls` |
| Agent | 把"模型说要调"变成"真的调了、结果再喂回去"的**循环** | `AiAgentService.run()` 的 for 循环 |

**最关键的一句话**（面试大概率会追问这里）：

> 模型自己不执行任何东西。它只是输出一段结构化文本说「我要调 `search_blogs`，参数是 `{"keyword":"Vue"}`」。
> 真正去查数据库的是**我的 Java 代码**。模型的价值在于它自己决定**调哪个、传什么参**——这是它和关键词搜索的本质区别。

如果你的简历写了 function calling 却答不出这句，会当场露馅。

## 第 2 章 一次对话到底发生了什么

### 2.1 看真实报文

下面是从你本机抓的**原始 SSE 输出**（`curl` 直接拿的，没做任何过滤），问的是「站内有多少篇文章？」：

```
event:meta
data:{"chatLogId":13,"model":"deepseek-chat","tools":["get_blog_detail","create_blog_draft","search_blogs","get_blog_stats"]}

event:tool_call
data:{"name":"get_blog_stats","arguments":"{}"}

event:tool_result
data:{"name":"get_blog_stats","success":true,"durationMs":4,"preview":"【站点概览】\n文章总数：6\n累计阅读量：49\n..."}

event:content
data:{"text":"站"}

event:content
data:{"text":"内"}

...（后面几百行，每个字一个 content 事件）...

event:done
data:{"iterations":1,"promptTokens":901,"completionTokens":47,"durationMs":623,"chatLogId":13}
```

### 2.2 这六种事件分别代表什么

| 事件 | 谁产生的 | 前端拿它做什么 |
|---|---|---|
| `meta` | 后端开场 | 显示可用工具列表、记录会话 ID |
| `tool_call` | 后端（模型决定的） | 立刻显示「正在检索…」 |
| `tool_result` | 后端（工具执行完） | 把提示改成「已检索站内文章 4ms」 |
| `content` | 后端（模型吐字） | 追加到气泡里，形成打字机效果 |
| `done` | 后端收尾 | 显示「1 次工具调用 · 623ms · 948 tokens」 |
| `error` | 后端兜底 | 在气泡里显示失败原因 |

### 2.3 完整链路（把这张图背下来）

```
浏览器 fetch GET /ai/chat?message=...
        │
        ▼
① AiAgentController.chat()          ← 还在 Tomcat 请求线程上！
        │  这里必须做完一件事：把登录身份抓出来（见 3.2）
        ▼
② aiAgentExecutor 线程池             ← 换线程了，ThreadLocal 从此失效
        ▼
③ AiAgentService.run()
        │  先写一条 ai_chat_log（status=RUNNING）拿到主键
        │
        └──► for (round = 0; round < 5; round++)
                 │
                 ├─ DeepSeekClient.chatStream(messages, tools)
                 │
                 ├─ 有 tool_calls ？
                 │     ├─ 有 → ToolRegistry.invoke() 执行工具
                 │     │        ├─ 权限校验
                 │     │        ├─ 落 ai_tool_call_log
                 │     │        └─ 结果作为 role=tool 消息塞回 messages
                 │     │        然后进下一轮
                 │     └─ 没有 → 把正文流式推给前端，break
                 │
                 └─ 第 5 轮还在调工具 → 去掉 tools 再问一次，逼它作答
        ▼
④ 回填 ai_chat_log（status=SUCCESS + tokens + 耗时），推 done 事件
```

## 第 3 章 三个最难的地方（面试主战场）

### 3.1 流式解析：为什么必须按 index 聚合

**问题**：模型流式返回工具调用时，参数不是一次性给全的。

第一片长这样：

```json
{"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_abc","function":{"name":"search_blogs","arguments":"{\"key"}}]}}]}
```

第二片：

```json
{"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"word\":\"Vue\"}"}}]}}]}
```

注意第二片**没有 id、没有 name**，只有 `arguments` 的碎片。你如果每片都当独立 JSON 解析，得到的永远是半个 JSON，`JSON.parse` 必炸。

**做法**（`DeepSeekClient.parseSse()`）：

```java
Map<Integer, AiToolCall>     callMap = new LinkedHashMap<>();  // index → 工具调用
Map<Integer, StringBuilder>  argBuf  = new LinkedHashMap<>();  // index → 参数拼接缓冲

// 每个分片：
int index = tc.path("index").asInt(0);
AiToolCall acc = callMap.computeIfAbsent(index, k -> new AiToolCall());
if (acc.getId() == null && tc.hasNonNull("id"))       acc.setId(tc.get("id").asText());
if (acc.getName() == null && fn.hasNonNull("name"))   acc.setName(fn.get("name").asText());
if (fn.hasNonNull("arguments"))                       argBuf.get(index).append(fn.get("arguments").asText());

// 流结束后：call.setArguments(argBuf.get(index).toString())  ← 这时才是完整 JSON
```

**面试可以这样收尾**：这段逻辑没法靠框架省掉，用官方 SDK 会帮你做，但我这个项目 `java.version` 是 1.8，引不了新依赖，所以是用 `HttpURLConnection` 自己读 InputStream 逐行解析的——顺带也把 SSE 协议搞明白了，`data:` 前缀、空行分隔、`[DONE]` 结束标记这些。

### 3.2 跨线程身份：ThreadLocal 为什么会失效

**这是整个改造里最有价值的一个坑，也是最能体现你水平的一处。**

你项目里拿当前用户的写法是：

```java
// TokenUtils.getCurrentUser()
HttpServletRequest request = ((ServletRequestAttributes) RequestContextHolder.getRequestAttributes()).getRequest();
```

`RequestContextHolder` 底层是 **ThreadLocal**——它只在「正在处理这个 HTTP 请求的那条线程」上有效。

而 Agent 为了做流式输出必须换线程（见链路图第 ② 步）。一旦换了线程：

1. `RequestContextHolder.getRequestAttributes()` 返回 `null`；
2. 你的 `getCurrentUser()` 有 `try/catch`，异常被吞掉；
3. **它返回一个 `new Account()` —— 一个空对象**；
4. 于是 `role` 是 null、`id` 是 null。

最坏的地方在于：**不报错**。没有异常、没有日志，只是权限判断静默失效、写进去的数据没有作者。

**做法**（`AiAgentController.chat()`）：

```java
// 在请求线程上，一次性把身份快照出来
Account currentUser = TokenUtils.getCurrentUser();
final AgentContext context = new AgentContext(
        currentUser.getId(), currentUser.getUsername(),
        currentUser.getName(), currentUser.getRole());

// 再交给线程池，context 作为参数显式传下去
aiAgentExecutor.execute(() -> aiAgentService.run(question, context, new SseAgentListener(emitter)));
```

`AgentContext` 是个不可变对象，全程靠参数传递，不依赖任何 ThreadLocal，天然线程安全。

**你手上有一组活体证据**（真实数据，出自 `ai_chat_log` 表）：

| 会话 ID | 时间 | 修复状态 | user_id | 可用工具数 |
|---|---|---|---|---|
| 1 | 10:21:24 | 修复前 | **NULL** | 3 |
| 2 | 10:22:25 | 修复后 | 1 | 4 |

会话 1 那行 `user_id=NULL`，就是身份丢失的现场。面试时如果能说出「我一开始也踩了，后来用这组对照数据定位的」，比背正确答案强十倍。

顺带说：这个坑还暴露了第二个缺陷——`JwtInterceptor` 认证时支持从 **URL 参数**取 token，但 `TokenUtils` **只认 header**。两者不一致，导致「拦截器放行了、业务层拿不到用户」。这个缺陷在原有页面上永远暴露不出来（前端统一走 header），是 SSE 场景把它逼出来的。已修复。

### 3.3 权限：为什么写工具要做两道关

`create_blog_draft` 是唯一有副作用的工具。它被两道防线管着：

**第一道（声明层）**——`ToolRegistry.buildToolSpec(context)`：

```java
for (AiTool tool : toolMap.values()) {
    if (tool.adminOnly() && !context.isAdmin()) {
        continue;   // 普通用户的工具列表里根本没有它
    }
    ...
}
```

为什么要在声明层就裁掉，而不是让它调用失败？因为**模型看不到这个工具，就不会去尝试**。
如果不裁，模型看到「有个创建文章的工具」，它会在用户要求发文章时兴冲冲地调，然后收到一个「无权限」的错误，再回头跟用户解释——体验差、浪费 token，还可能让用户误以为「有权限但失败了」。

**第二道（执行层）**——`ToolRegistry.invoke()` 里再校验一次：

```java
if (tool.adminOnly() && !context.isAdmin()) {
    return "拒绝执行：工具 X 需要管理员权限";
}
```

兜底，防止有人绕过声明层直接构造调用。

**验证数据**（同一套代码、同一时刻，只换账号）：

| 账号 | 角色 | `available` 工具数 | 问「帮我写篇vue文章并发布」的结果 |
|---|---|---|---|
| admin | ADMIN | 4 | `iterations=2`，真的写出文章 id=23 |
| light | USER | 3 | `iterations=0`，直接如实说明无权 |

这张表可以现场演示，是最有说服力的一段。

## 第 4 章 其余五个设计点（被问到能答上就行）

### 4.1 为什么用 SSE 而不是 WebSocket

SSE 是**单向**的（服务端→浏览器），正好匹配「模型一直吐字、前端只负责显示」的场景。
WebSocket 是双向的，为这个场景引入连接管理、心跳、重连，属于过度设计。
另一层原因：`SseEmitter` 是 Spring MVC 自带的（servlet 栈），零新依赖。

### 4.2 为什么用 fetch 手动解析，不用 EventSource

原生 `EventSource` 有两个硬伤：
1. 只能发 GET；
2. **不能设置请求头**。

而你项目的鉴权 token 是放在 header 里的。所以前端用 `fetch` + `ReadableStream` 读流、自己按 `\n\n` 切事件块。好处是 token 走 header，不会进 access log。

### 4.3 为什么 `SseEmitter.send(String)` 会中文乱码

`send()` 传字符串时走 `StringHttpMessageConverter`，它的默认字符集是 **ISO-8859-1**。
必须 `.data(payloadObject, MediaType.APPLICATION_JSON)` 让 Jackson 转换器处理，输出 UTF-8。这个坑不踩一次不会知道。

### 4.4 为什么要独立线程池

SSE 连接一次占用线程几十秒。跑在 Tomcat 请求线程上，几十个并发就能把 Web 线程池吃光，**登录、文章列表这些普通接口全部排队**——AI 功能把主站拖垮是最典型的翻车方式。
所以 `AiExecutorConfig` 单独开池（核心 4 / 最大 16 / 队列 50 / CallerRunsPolicy），故障不扩散。

### 4.5 为什么要轮次熔断

模型在「查不到东西」时会反复调同一个工具。必须有硬上限（`ai.max-iterations: 5`）。
更巧的一点是**触顶后的收口**：不要直接返回空白，而是去掉 `tools` 再请求一次，逼模型用已经拿到的事实作答——用户至少能收到一个有内容的回答。

## 第 5 章 面试问答速查

**Q：你这个 Agent 和 RAG 有什么区别？**
A：RAG 是检索增强——把文档切片向量化，按语义相似度召回，再让模型基于召回内容回答；核心是**向量检索**。我做的是 function calling——模型自己决定调哪个工具、参数是什么，工具内部就是原生的 MyBatis 查询。这个项目里没有向量库，检索走的是 SQL 的 `like`。两者解决的问题方向不同：RAG 解决「模型不知道你的私有知识」，function calling 解决「模型不能操作你的系统」。

**Q：那你这不算真正的 Agent 吧？**
A：取决于定义。如果是「多轮自主规划、长期记忆、能自我反思」，那确实不算——我是单轮工具调用循环 + 轮次上限。但如果定义是「模型自主决策 + 调用外部工具 + 根据结果继续推理」，这就是标准 Agent 循环（ReAct 范式的简化版）。我刻意没做无限自主，因为这是个博客站，可控性比自主性重要。

**Q：模型会不会乱调工具？**
A：会。我遇到两种：一是查询为空时反复调同一个工具（用轮次上限挡住）；二是它把用户指定的文章标题自己改写了（属于模型行为层面，靠 system prompt 压制，但不能 100% 保证）。所以我不会让 Agent 碰任何不可逆操作——目前唯一的写工具是**创建草稿**，不是直接发布。

**Q：怎么调试 Agent？**
A：两张审计表。`ai_chat_log` 记每次提问的回答、工具轮次、token、耗时；`ai_tool_call_log` 记每次工具调用的入参、返回、成功与否、耗时。出问题直接查库就能回答「它查了什么、看到了什么、花了多少」——Agent 的调试难点在于行为不确定，没有 trace 就是黑盒。

**Q：token 消耗多少？**
A：实测单次只读问答约 1800-2000 输入 token、150-200 输出；让模型写长文则 2600+750。因为工具返回结果做了 4000 字符截断，检索结果只回摘要不回正文，不然上下文会被撑爆。

**Q：为什么工具只有 4 个？**
A：工具数量越多，模型选错的概率越高。我把「统计」类问题用一个 `get_blog_stats` 全覆盖，而不是给每类统计各开一个工具。经验值是控制在 5-10 个以内。

**Q：新增一个工具要改多少代码？**
A：写一个实现 `AiTool` 接口的类，加 `@Component`。注册表是 Spring 注入 `List<AiTool>` 自动发现的，主循环、协议拼装、权限校验、审计落库全都不用动。这是我刻意的设计——工具是扩展点，不该让它反过来逼着主流程改。

## 第 6 章 你可以自己动手改的地方（练习）

按难度排序，都值得你亲手做一遍，做完面试就有底气了：

1. **加一个只读工具**：实现 `comment` 相关的工具，比如「查某篇文章的最新评论」。
   *验证*：用 `curl` 问「id=12 这篇文章有什么评论」，看 `ai_tool_call_log` 里有没有新记录。

2. **改审计日志的粒度**：现在 `tool_result` 显示耗时，试着再加一个「本轮模型思考耗时」。
   *验证*：前端 `done` 事件里能同时看到两段时间。

3. **给工具加缓存**：`BlogSearchTool.parameters()` 每次请求都查一次分类表，把分类列表缓存 60 秒。
   *验证*：连续问两个问题，第二次的 SQL 日志里不该出现 `select id,name from category`。

4. **多轮对话**（难度最高）：让前端把历史消息带上，后端把 `messages` 从历史里重建。
   *提示*：`ai_chat_log` 的表结构已经能撑，但要加个会话 ID 把多条记录串起来。
